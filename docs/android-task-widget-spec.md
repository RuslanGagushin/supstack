## Цель и границы

Пользователь видит просроченные задачи и задачи на сегодня на домашнем экране, даже если Supstack закрыт. Из виджета можно открыть задачу или начать добавление новой. Todoist — ориентир по сценарию использования.

Первый релиз: один прокручиваемый виджет «Сегодня» с изменяемым размером. Во втором релизе — завершение задач галочкой прямо в виджете. Выбор блокнотов и тегов, несколько видов списков и ввод новой задачи без открытия приложения — отдельные улучшения без обязательства включить их в эти два релиза.

## 1. Первый релиз: просмотр и переход в приложение

| Сценарий | Ожидаемое поведение |
| --- | --- |
| Добавить виджет из меню Android | В списке виджетов есть «Supstack — Сегодня». Экземпляры можно добавлять и удалять независимо; все показывают текущее хранилище приложения. |
| Посмотреть задачи | Сначала раздел «Просрочено», затем «Сегодня». Пустые разделы скрыты. Если оба пусты, показано «На сегодня задач нет». Заголовок и `+` остаются доступны при прокрутке. |
| Нажать на задачу | Supstack открывает нужную задачу по её ID, в том числе при холодном запуске. Если задача удалена или хранилище сменилось, открывается «Сегодня» с пояснением. |
| Нажать на заголовок или `+` | Заголовок открывает «Сегодня»; `+` открывает существующую форму быстрого добавления. Сам тап не создаёт задачу. Если хранилище ещё не выбрано, сначала открывается его выбор. |
| Изменить размер или тему | Список прокручивается при любой поддерживаемой высоте. Длинные названия сокращаются только визуально. Светлая и тёмная темы, крупный системный шрифт и TalkBack поддерживаются; у `+` есть текстовое имя для озвучивания. |
| Нет актуальных данных | До первой загрузки — «Откройте Supstack, чтобы загрузить задачи». При недоступном хранилище или устаревшем снимке — «Откройте Supstack, чтобы обновить задачи». Это отдельные состояния, отличимые от пустого списка. |

### Компоновка по референсу Todoist

- Начальный размер — 4 × 2 ячейки там, где лаунчер поддерживает это указание. В компактной шапке слева знак Supstack и «Сегодня», справа круглая кнопка `+` в синем акценте Supstack.
- Строки разделены тонкими линиями. Слева у каждой строки — контурный круг открытой задачи; вся строка открывает задачу. Завершение по кругу входит во второй релиз.
- Когда просроченных нет, задачи на сегодня идут сразу под шапкой, без повторного заголовка. При наличии обоих разделов заголовки помогают их различать.

### Какие задачи показывать

- Использовать правила повестки (`orgDayEntries` в `web/src/js/core/org.js`): открытые задачи, просроченные или запланированные либо со сроком на выбранный день, включая повторения по правилам Supstack. События, завершённые записи, чек-листы заметок и предупреждения о будущем сроке (`soon`) не показывать. Фильтры открытой повестки на виджет не влияют.
- Одна строка на ID задачи. Если повестка одновременно относит задачу к «Просрочено» и «Сегодня», она показывается в «Просрочено». Внутри раздела сохраняется порядок повестки.
- Сегодняшняя дата определяется по локальному календарю Android, а не по UTC.

### Данные и интеграция

Нативный Android App Widget реализуется в существующем Kotlin-модуле `tauri-plugin-vault/android`, с системной разметкой `RemoteViews`. На техническом прототипе проверить, что виджет виден и в APK, собранном через чистый `tauri android init --ci`, как в `.github/workflows/apps.yml`.

Приложение рассчитывает список на основе `web/src/js/services/tasks.js` и передаёт Android версионированный снимок на **сегодня и следующие шесть локальных дней**. Для каждого дня достаточно хранить ID задачи, заголовок, раздел и порядок; для снимка — идентификатор хранилища, часовой пояс и время формирования. Снимок заменяется целиком в приватном хранилище приложения. `.supstack/tasks.jsonl` остаётся источником данных, формат хранилища не меняется.

- Обновлять снимок после загрузки хранилища, успешной записи задач и перечитывания файла после синхронизации. При смене или отключении хранилища сразу очистить старый снимок; запоздавшее обновление от прежнего хранилища игнорировать.
- Нативный код выбирает список для текущего дня из снимка, даже без WebView и сети. Перерисовывать при смене даты или часового пояса и через плановое обновление, если системное событие пропущено. Точное обновление в полночь не гарантируется: Android может отложить фоновые вызовы. Если для текущей даты нет списка или часовой пояс снимка отличается, показать состояние устаревших данных до пересчёта приложением.
- Виджет отражает последнюю успешно загруженную копию. Он не запускает Git-синхронизацию самостоятельно. Переходы обрабатываются и при запуске, и в уже открытом приложении; ID задачи разрешается после загрузки хранилища.

## 2. Второй релиз: завершение прямо в виджете

- Галочка работает без открытия Supstack. Обычная задача после подтверждённого сохранения исчезает из списка; повторяющаяся обрабатывается по тем же правилам, что и в приложении (`web/src/js/core/tasks.js`), и может остаться в списке, если следующая дата всё ещё относится к текущему дню.
- Действие адресуется конкретному хранилищу, ID задачи и отображённой версии записи. Исполнитель перечитывает актуальное состояние перед изменением. Повторный тап, повтор доставки после перезапуска и действие по старому снимку не должны завершить задачу дважды или продвинуть повторение два раза.
- Изменение проходит через единый путь записи, согласованный с редактированием в приложении и синхронизацией. До начала реализации выбрать и проверить, как выполнять общую логику перехода состояния без WebView. Отдельный Kotlin-путь, который перезаписывает файл из снимка, не подходит.
- Пока запись не подтверждена, показать ожидание. Если задача изменилась после синхронизации, обновить строку и дать пользователю повторить действие явно. При ошибке записи вернуть обычное состояние и показать ошибку. Успешное локальное изменение попадает в штатную синхронизацию; сеть для завершения не обязательна.

**Что выяснили для прототипа:** на Android и приложение, и обратная запись из Git-зеркала используют `VaultPlugin.write`, но подготовка изменений происходит отдельно и раньше этой команды. Блокировки только на последней записи недостаточно. Прототип должен проверить обновление с проверкой версии файла перед записью для всех трёх путей: приложения, синхронизации и виджета. Семантику повторений нужно сверить с тестами существующей JS-логики.

## 3. Цикл разработки и приёмки

| Этап | Результат и условие перехода |
| --- | --- |
| **Проверка подхода** | Собрать APK в штатном Android-процессе. На эмуляторе и физическом телефоне проверить регистрацию виджета, список из сохранённого снимка при выгруженном процессе и доставку тапа при холодном и тёплом запуске. |
| **Реализация первого релиза** | Подключить расчёт списка, снимки, экранные состояния и навигацию. Добавить тесты отбора и порядка: просрочка, срок и план на один день, повторение, исключение будущих предупреждений, события и закрытые задачи. |
| **Приёмка первого релиза** | Установить APK поверх предыдущей версии и с нуля. Проверить два экземпляра виджета; изменение размера и темы; крупный шрифт и TalkBack; открытие задачи и `+`; обновление после локальной правки и синхронизации; смену дня при выгруженном процессе, перезагрузку, смену часового пояса и хранилища. После смены хранилища старые заголовки не видны. |
| **Бета и выпуск первого релиза** | Раздать тестовый APK. После исправлений повторить сценарии на стандартном и хотя бы одном OEM-лаунчере. Выпускать после прохождения CI и приёмки Android; в changelog описать, как добавить виджет и как он обновляется. |
| **Реализация и выпуск галочек** | Сначала подтвердить общий путь записи без WebView. Затем проверить обычную и повторяющуюся задачу, двойной тап, остановку процесса между записью и подтверждением, офлайн-режим, отзыв доступа к папке и одновременную правку или синхронизацию. Критерий выпуска: ни одна правка не теряется, повторение сдвигается только один раз, ошибка не показывается как успех. |

**Оценка:** первый релиз — 2–4 рабочих дня; с галочками — 5–8 дней суммарно, если прототип подтвердит общий путь записи без WebView. Если для этого требуется перенос части логики задач из JS, оценка второго этапа уточняется после прототипа. Календарное время на бета-тестирование в оценку не входит.
